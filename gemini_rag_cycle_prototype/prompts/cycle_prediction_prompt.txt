You are estimating source-level execution time for a not-yet-compiled C task.

This is an engineering source-level point estimate, not a formally proven WCET
bound. Analyze only the supplied C source, hardware profile, context, and
retrieved measured references. Do not assume access to ELF, assembly, map,
disassembly, compiler output, or a new board measurement. Do not delegate the
estimate to an external deterministic cycle calculator.

ESTIMATE DEFINITION
- Produce one `estimated_source_execution_cycles` value and its corresponding
  `estimated_source_execution_us` value.
- The estimate is the sum of source-visible dynamic work and only those
  compiler-sensitive or hardware-sensitive contributions supported by supplied
  evidence.
- It is not a complete hardware WCET bound. Always return
  `formal_guarantee=false`.
- Do not target a desired error percentage or bias. Do not add a safety margin
  merely to make the result conservative.

SOURCE ANALYSIS RULES
- Initialization is outside the timed function unless explicitly stated.
- Resolve bounded loops and feasible source-level paths.
- Follow helper functions only when their bodies are supplied.
- If a critical loop bound or helper body is missing, return PARTIAL or
  UNRESOLVED and explain what is missing.
- Never price a loop body only once. Convert operations, branches, memory
  accesses, and helper calls inside loops to dynamic execution counts.
- Multiply nested-loop bounds along the complete nesting path. A helper called
  once in a 6 by 6 loop executes 36 times.
- Expand each supplied helper body separately and multiply its work by the
  dynamic call count at every call site. Do not count only call/return overhead
  while omitting the callee body.
- Account for loop initialization, condition checks including the final failed
  check, increments, addressing, loads, stores, arithmetic, comparisons,
  branches, call overhead, and callee work.
- Identify the feasible source path whose priced work is highest. Do not invent
  an input path that contradicts supplied source constraints.
- Retrieved records contain measured board references. Use them only when
  structural differences and similarities are explicitly reconciled. Do not
  copy a measured value without analysis.
- In `retrieved_examples_used.task_id`, copy the complete supplied reference ID.

CYCLE COMPONENT RULES
- Return `cycle_components` and separate at least these concepts:
  1. `source_visible_work`: caller operations, loop control, branches, and
     source-visible memory work.
  2. `resolved_helper_work`: expanded helper bodies and justified call overhead.
  3. `compiler_sensitive_overhead`: stack spills, instruction selection, and
     other compiler-dependent work not established by supplied evidence.
  4. `pflash_fetch_overhead`: PFlash wait-state/prefetch contribution.
- A priced component has an integer `cycles` value and specific evidence.
- An unpriced component has `cycles=null` and evidence explaining why it cannot
  be priced.
- `estimated_source_execution_cycles` must equal exactly the sum of all
  non-null component cycle values. Null components contribute zero to that
  arithmetic because they are unknown, not because their physical cost is zero.

UNPRICED HARDWARE RULE
If an exact compiler-sensitive or hardware-sensitive timing contribution is not
supported by the supplied hardware profile or a structurally relevant retrieved
board reference:
1. Set that component's cycles to null.
2. Add the missing contribution to both `unresolved` and `warnings`.
3. Do not convert it into a percentage, multiplier, wait-state count, CPI, or
   invented cycle allowance.
4. Do not add it to `estimated_source_execution_cycles`.
5. Return `analysis_status=PARTIAL`.
6. Still return the required point estimate for the components that can be
   priced from source and supplied evidence.

FORBIDDEN UNSUPPORTED ASSUMPTIONS
- Assuming one or another number of Flash wait states.
- Multiplying by 1.3, 1.6, or any other unsupported factor.
- Adding a generic compiler, stack, Flash, cache, or uncertainty percentage.
- Inventing CPI or instruction counts from general Cortex-M4 knowledge.
- Claiming zero-wait-state instruction fetch because data is in SRAM.
- Citing generic dynamic branch prediction, cache misses, unaligned accesses,
  DMA stalls, or interrupt interference without supplied evidence.

MANDATORY PROCEDURE
1. Identify every bounded loop nesting path and the selected feasible path.
2. Derive dynamic caller-operation, memory, branch, and helper-call counts.
3. Expand supplied helper bodies, including their internal bounded loops.
4. Create the cycle components. Price only evidence-supported contributions.
5. Sum only non-null components into `estimated_source_execution_cycles`.
6. Convert cycles to microseconds using the supplied hardware clock and verify
   the two representations agree.
7. If two bottom-up reconstructions disagree, report the discrepancy. Select a
   value only when one reconstruction has stronger supplied evidence. Do not
   select the larger value solely because it is larger.
8. In `estimation_reasoning_summary`, show decisive dynamic counts and compact
   arithmetic matching the component sum.
9. Audit assumptions against the supplied profile. Put unavoidable unknowns in
   `unresolved` and `warnings`; never hide them inside the point estimate.
