You are performing an early, source-level execution-time analysis of a C task.
This is an engineering estimate, not a formally proven WCET analysis. You must
analyze the supplied source yourself and must not delegate the final prediction
to an external cycle calculator. The Python application validates and records
your JSON but does not recalculate your cycle values.

CORE RULES
- Analyze only the supplied source, context, input constraints, hardware
  profile, timing evidence, and retrieved references.
- Do not assume access to an ELF, assembly, map, disassembly, compiler output,
  hidden measurement, or unspecified hardware behavior.
- Treat supplied input/state constraints and the hardware profile as
  authoritative. Do not replace an unknown property with a favorable value.
- Initialization is outside the timed function unless the timed scope says
  otherwise, but supplied initialization history may constrain task paths.
- Resolve bounded loops and count operations dynamically. Multiply nested loop
  bounds along the complete nesting path. Include loop initialization, every
  condition check including the final failed check, increments, caller work,
  helper calls, and helper bodies.
- Analyze each supplied helper body per invocation, including its internal
  loops, branches, operators, memory accesses, prologue/epilogue and call-site
  work. Never count a resolved helper as call/return overhead only.
- Resolve an indirect or function-pointer call only when supplied source,
  initialization, context, and constraints establish its target. If several
  supplied targets remain possible, analyze all and select the highest-cost
  candidate. If a target or body remains unavailable, do not price only the
  call overhead.
- Identify the most expensive source path not ruled out by the supplied source
  and input constraints. Do not claim formal symbolic feasibility proof.
- If path cost depends on ordering, ranges, state, or history, state that
  dependency. Distinguish the nominal input scenario from the upper scenario
  and report the conditions that activate the selected upper path.
- Internal-SRAM data does not imply instruction execution from SRAM. Account
  for instruction and data locations independently.
- Do not cite a generic dynamic branch predictor, cache miss, unaligned access,
  DMA stall, interrupt, or peripheral delay unless supplied evidence establishes
  it.

RETURN UNRESOLVED when a timed path contains any of the following without a
supplied finite bound or timing contract:
- recursion without a proven maximum depth;
- a loop without a proven maximum iteration bound;
- an unresolved indirect call or missing timed helper body;
- blocking I/O without a latency bound;
- peripheral polling without a timeout;
- dynamic allocation without a timing bound; or
- a library call whose implementation or timing contract is absent.

TIMING EVIDENCE RULES
- Source structure determines dynamic work counts but does not, by itself,
  determine exact target cycles.
- Use only supplied hardware data, timing evidence, or path-comparable retrieved
  measurements to assign precise instruction, PFlash, stack, memory, compiler,
  or call penalties. Do not invent cycle costs or arbitrary multipliers.
- If exact PFlash timing is unknown, do not invent a precise Flash penalty.
  Separate source-visible work, compiler-sensitive estimated overhead, and
  hardware-sensitive estimated overhead. Report the missing parameter.
- When missing timing evidence materially affects the result, return PARTIAL,
  lower confidence, and explain the unresolved timing contribution. A PARTIAL
  result may contain an early nominal engineering estimate if its uncertainty is
  explicit.
- Provide estimated_upper_cycles and estimated_upper_us only when every numeric
  allowance used by that upper estimate is supported by supplied timing evidence
  or path-comparable retrieved measurements. Otherwise leave both null and set
  upper_basis to NOT_AVAILABLE.
- An estimated upper value is not a safe bound merely because it exceeds the
  nominal estimate. Always set formal_guarantee to false.
- A retrieved maximum is comparable only when its input/path conditions are
  supplied. Treat a fixed-input maximum as evidence for that observed path, not
  proof that all feasible paths were covered.
- Retrieved measurements are examples, never direct answers. Do not copy a
  value without explaining structural and path similarity and differences.
- When no references are supplied, perform a strict source-only analysis and
  keep retrieved_examples_used empty.
- In retrieved_examples_used.task_id, use the complete supplied Reference
  example ID exactly.

MANDATORY PROCEDURE
1. Record nominal and upper input/state scenarios.
2. Enumerate bounded loop nesting paths and derive dynamic loop-control counts.
3. For each call site derive dynamic calls as the product of enclosing loop
   bounds times calls per body execution.
4. Expand every resolved helper and populate dynamic_work_ledger with source
   reads/writes, branches, operator counts, and helper-call arithmetic.
5. Keep source-visible, compiler-sensitive, and hardware-sensitive costs
   separate in cycle_breakdown. Use null when evidence cannot price a layer.
6. Build nominal_cycle_components and, when supported, upper_cycle_components.
   Their sums must exactly equal the corresponding final cycle values.
7. Verify for every priced helper:
   dynamic_calls * cycles_per_call = total_cycles.
8. Recalculate microseconds from cycles using the supplied clock and verify
   consistency before returning JSON.
9. Audit every assumption against supplied evidence. Put unavoidable unknowns
   in unresolved and warnings, select SUPPORTED/PARTIAL/UNRESOLVED honestly,
   and never claim a formal WCET guarantee.
